# Project Flint 0.1.0-alpha.10 — Knapping Transaction Fix

## Intent
Fix the two concrete regressions reported after alpha.9 without changing accepted balance: knapping outcomes behaving differently depending on whether the offhand hammerstone was swapped, and dragged inventory items rendering underneath primitive locked-slot art.

## Player-facing behavior
- Knapping still requires a Rock in each hand and eight valid strikes per completed attempt.
- Completed attempts still have a 68% success chance.
- Failure consumes only the main-hand working Rock.
- Success transforms only the main-hand working Rock into a Refined Rock.
- The offhand hammerstone is never consumed or replaced and changing it is no longer relevant to success/output handling.
- Dragged/held item sprites now render above locked inventory-slot shading instead of disappearing beneath it.
- No other inventory restrictions, stack limits, Twig Pile behavior, worldgen, animal balance, or primitive-action timings are changed.

## Architecture introduced
No new subsystem is introduced. The knapping completion result is now returned from `StoneWorkingSystem` as an explicit `IN_PROGRESS`, `SUCCESS`, or `FAILURE` result. `RockItem#use` applies the final main-hand stack change with `InteractionResult.Success#heldItemTransformedTo`, keeping that mutation inside Minecraft's normal item-use transaction rather than editing the selected inventory slot mid-transaction.

The locked-slot overlay is rendered from `InventoryScreen#renderBg` instead of the tail of the full `render` method. It remains purely cosmetic; server-side slot locking is unchanged.

## Design reasoning
Alpha.9's packaged patch contained the `StoneWorkingSystem` output-delivery change but accidentally omitted the matching `RockItem.java` transaction change. That left the shipped build mutating the main-hand stack/inventory from inside `Item#use`, where Minecraft can subsequently reconcile the hand stack as the use transaction finishes. This made the observed result depend on later inventory synchronization, including swapping the offhand Rock.

The correct fix is not to alter the 68% RNG. The server decides the attempt result once; the item-use result then authoritatively transforms the main-hand working Rock. The hammerstone has no state in the roll.

Likewise, locked-slot art should visually describe unavailable slots, not sit above interactive item sprites. It therefore belongs in the inventory background pass.

## Tuning snapshot
- Stone-working strikes per attempt: unchanged at 8.
- Stone-working success chance: unchanged at 68%.
- Completed failure cost: 1 main-hand Rock.
- Completed success conversion: 1 main-hand Rock → 1 Refined Rock.
- Offhand hammerstone cost: 0.
- All other accepted alpha.9 tuning remains unchanged.

## Assets and licensing
No assets were added or changed in this release. No third-party content is introduced.

## Validation performed
- Parsed all JSON resources using the existing release validator.
- Verified `RockItem` is included in this patch.
- Verified successful and failed completion paths use `heldItemTransformedTo` for the main hand.
- Verified `StoneWorkingSystem` no longer directly shrinks or inserts the working Rock/output.
- Verified the 68% success chance and eight-strike threshold are unchanged.
- Verified primitive lock shading is invoked only from `renderBg`, before slot/cursor item rendering.
- Verified server-side primitive slot locking itself is unchanged.

## Known limitations
The artifact environment still cannot perform the final Fabric client launch. The local build/client remains the final compile and runtime gate.

## Next pressure
Retest knapping with the same offhand Rock across many completed attempts and drag an item across locked slots. Do not retune knapping chance unless the corrected transaction path is confirmed and the remaining failure rate still feels too punishing.
