# Project Flint 0.31.18-b — PF-EMI Nested-JAR Build Hotfix

## Intent
Repair the v0.31.17-b PF-EMI jar-in-jar build wiring without changing its gameplay, quest, recipe-visibility, or tilling behavior.

## Player-facing behavior
No intentional gameplay changes. PF-EMI remains bundled inside Project Flint, Flint Quests workstation hooks remain active when Flint Quests is installed, unobtainable recipe pages remain hidden, and Loose Dirt/Loose Soil remain tillable with the Bone Hoe.

## Architecture
v0.31.17-b declared `libs/PF-EMI-1.21.11.jar` with Gradle `files(...)` for both `modImplementation` and Loom `include`. Java compilation succeeded, but Loom 1.14.10 rejected the raw file dependency during `processIncludeJars` because it had no module component/capabilities.

v0.31.18-b keeps the exact supplied jar in `libs/`, exposes that directory through Gradle `flatDir`, and declares PF-EMI by module name for both `modImplementation` and `include`. Gradle therefore resolves it as an external module component with a default capability, which is the metadata shape Loom's nested-JAR task requires.

## Design reasoning
The PF-EMI binary is intentionally left byte-for-byte unchanged. The fix is entirely in Project Flint's Gradle dependency declaration; there is no repacking, shading, or source modification of PF-EMI.

## Known limitations
Full Loom execution could not be rerun in the artifact environment because its plugin resolver cannot currently acquire Fabric Loom 1.14.10. The dependency shape itself was separately verified with Gradle 9.2.1: a `flatDir` dependency resolves as a `ModuleComponentIdentifier` and exposes a default capability, directly addressing the exact `processIncludeJars` error reported by the local Project Flint build.
