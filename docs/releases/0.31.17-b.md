# Project Flint 0.31.17-b — Quest Hooks, Nested PF-EMI, and Recipe Visibility

## Intent
Integrate the new Flint Quests custom-event API into Project Flint's bespoke workstation progression, bundle the supplied Project Flint EMI fork directly inside the Project Flint distribution, keep EMI aligned with actual Project Flint progression, and fix the Bone Hoe's inability to till Loose Dirt/Loose Soil.

## Player-facing behavior
- PF-EMI is now distributed as a nested Fabric mod inside Project Flint; players do not need a second standalone EMI jar for the Project Flint build.
- EMI only exposes recipe pages backed by currently implemented Project Flint processing routes. Vanilla/future/unimplemented recipe pages are hidden for now instead of advertising progression that cannot be reached.
- EMI has Project Flint categories for the Clay Grinder, Wooden Grinder, Sanding Station, Bookshelf, Primitive heat/Oven processing, and Advanced Kiln casting.
- Parchment-gated Primitive Oven recipes show the required inscribed Recipe Parchment as an ingredient.
- Loose Dirt and Loose Soil can now be tilled by the Bone Hoe under the same water/clearance rules as Grass Blocks.
- Flint Quests CUSTOM_EVENT tasks can react to Project Flint workstation operations.

## Architecture
- `FlintQuestsBridge` resolves the stable public `com.projectflint.flintquests.api.FlintQuestHooks.trigger(ServerPlayer, String, int)` method only when Flint Quests is loaded, keeping Flint Quests optional at compile/runtime.
- `WorkstationQuestEvents.CRAFT` remains a Project Flint-owned Fabric event and is also exposed through Fabric Loader ObjectShare for other integrations.
- Workstation events are emitted for Clay Grinder, Wooden Grinder, Sanding Station, Bookshelf, Primitive Oven, Advanced Kiln, Baked Kiln, Mortar Kiln, Primitive Campfire, and Lumber Processor operations; result-slot stations report the player claiming the result, direct heat processors report the player starting a valid process, and Lumber Processor formation has a bespoke formation event.
- `ProjectFlintEmiPlugin` owns the visible Project Flint EMI recipe catalog and removes non-Project-Flint recipe pages before re-registering progression-valid routes.
- `libs/PF-EMI-1.21.11.jar` is a local mod dependency and Loom `include` dependency so the final Project Flint jar receives it as a Fabric nested jar.

## Design reasoning
Project Flint deliberately replaces normal Minecraft recipe/progression assumptions. A generic recipe viewer that displays every vanilla recipe therefore teaches invalid shortcuts and future content. EMI should be useful as an in-game reference without becoming a progression leak, so this release exposes only recipes backed by a real Project Flint workstation/process.

Flint Quests already detects generic obtain/break/use/interact tasks itself. Project Flint only needs to report bespoke operations that the quest engine cannot infer, so workstation completion is sent through the public CUSTOM_EVENT hook rather than adding Flint Quests-specific logic to each quest definition.

## Assets and licenses
No Project Flint visual assets were added or replaced. The supplied PF-EMI jar is bundled unmodified as the requested nested dependency. Its embedded Fabric metadata identifies it as the MIT-licensed ProjectFlint-maintained EMI fork based on EMI.

## Advancement coverage
No Project Flint advancement definitions changed. This release adds Flint Quests custom-event integration rather than replacing or rewriting the existing Project Flint advancement tree.

## Known limitations
- Flint Quests remains optional and is not nested into Project Flint. If Flint Quests is absent, Project Flint workstation events simply have no Flint Quests consumer.
- Recipe visibility is intentionally conservative for this release: recipes outside Project Flint-owned progression categories are hidden from EMI, even if another unrelated mod could theoretically make one of them usable.
- The artifact environment cannot complete the normal Loom Gradle build because Fabric Loom `1.14.10` is unavailable to its plugin resolver; local `build.bat` remains the final full nested-jar/runtime validation gate.
